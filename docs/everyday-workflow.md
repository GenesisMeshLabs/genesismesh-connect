# Everyday Connect workflow

This is the normal application flow. Keys, authority URLs, transport tickets,
attestation IDs and policy IDs stay inside the native implementation. Technical
controls remain available under Settings → Advanced tools.

## Set up the network computer

On a supported desktop build, choose **Start on this computer**, name the network and computer,
then choose **Create my network**. The bundled Genesis Mesh 1.8.1 runtime uses
the real core initializer and authority routes. End users do not need Python,
a source checkout, WSL or a separately started authority. The authority listens
only on loopback and follows the Connect application's lifetime.

**Use an existing network on this computer** opens a native settings-file
picker. It reads the selected local Genesis Mesh TOML configuration and uses
that authority's root and operator identity. The existing authority must be
running on a numeric loopback address. Connect does not replace existing device
profiles or network roots. Existing technical profiles can still use Advanced.

Managed root, authority and operator key files are protected with account-scoped
Windows DPAPI after initialization. macOS/Linux desktop helpers use the native
credential store through their private pipe to the Rust host. The owner adapter accepts only fixed local
pipe operations; private keys and arbitrary administrative HTTP routes are not
exposed to the web UI or phone.

## Keep a recovery file

**Settings → Recovery → Create recovery file** on the network computer saves
one encrypted file and shows its **recovery key** once: 32 letters and digits
in groups of four. Write the key down and keep it apart from the file; anyone
with both can restore the network. The file holds the authority's database
(a consistent snapshot taken while it runs), its settings and genesis block,
the owner keys, and the network computer's own device identity and verified
trust history. Other devices are not in it; they keep their own identities.

On another computer, **Restore my network from a recovery file** on the
welcome screen brings the network back: the authority with its history, the
same network computer identity (so every paired device keeps trusting it), and
owner keys protected again by that computer's DPAPI or credential store.
Settings move to the new location. Devices reconnect the next time they reach
the network computer; under public relays they find it anywhere, and in
private mode on the same network. Choose shared folders again on the new
computer. A restore never replaces an existing network, and a wrong key or a
changed file leaves nothing behind.

The key is 160 random bits generated by Connect, never a password someone
chooses, so the file key is derived with HKDF-SHA256 and the contents are
sealed with AES-256-GCM, with the file header authenticated too. Networks
attached from an existing authority configuration are backed up with that
authority's own procedures instead.

A recovery file is a snapshot. Before relying on a restore:

- **Revocations made after the file was written are not in it.** A device you
  revoked later becomes trusted again on the restored network; revoke it again
  right after restoring. The same holds for devices added later: pair them again.
- **Retire the original computer.** Both copies hold the same network computer
  identity, but their authorities no longer agree. Do not run the old one again
  after restoring; erase its Connect data if you still have it.
- Create a new recovery file after changes you want to keep.

## Add the phone

1. On the computer, choose **Devices → Add device**.
2. Scan the QR with the phone's camera or copy its invitation into **Join a
   network**. Name the phone and choose **Ask to join**.
3. Compare the six-digit code on both devices, then choose **Allow device** on
   the computer. Declining, closing or consuming an invitation invalidates it.
4. Connect enrolls the phone and verifies an authenticated session in both
   directions. No key or transport ticket needs to be copied separately.

The join link expires after five minutes and produces one request. Approval
must arrive within two minutes. The link pins the network root, owner node and
temporary Iroh endpoint, plus a 256-bit secret. The owner proves its certificate
and node key before the client sends the secret. Both proofs bind challenges,
endpoint identities, roles, the Pair ALPN and the local TLS exporter. A name
alone never establishes identity. Invitations are bound to the proved client
node and enrollment still performs the existing authority/SDK verification.

The iPhone generates its own node key. Its private record uses a non-syncing
WhenUnlockedThisDeviceOnly Keychain item; the app container holds an opaque UUID
reference. Windows uses DPAPI. Separate persisted transport keys allow approved
devices to reconnect. How sessions and authority bridges find each other
depends on the network's connection setting (below). Address lookup does not
establish Genesis Mesh trust. The temporary pairing endpoint itself is never
published for lookup.

Keep both apps open and the computer awake. This is a foreground companion app,
not a system-wide VPN, background iPhone service or unattended Windows service.
The current controller supports up to 32 saved devices. Choose one by name in
Devices before browsing or checking a connection. Adding a second device keeps
the first. Existing single-device profiles migrate without replacing their
keys. See [platform evidence and limits](cross-platform.md).

Every device also learns the network's other devices from the network
computer: with each trust refresh it asks, over the authenticated authority
bridge, for the computer's saved devices and reports its own current address.
They appear in Devices as **On your network**, and devices connect to each
other directly, without going through the network computer. Being listed
grants nothing: every file operation still needs the authority's decision,
and a device that shares nothing with you says so. The network computer
decides who belongs, so a listed device cannot be forgotten on another device.
Opening Devices asks the network computer right away instead of waiting for
the next refresh.

### Remove a device

On the network computer, open **Devices**, then **More → Remove from network**
beside the device. On a server node, run
`sudo genesismesh-connect remove "Device name"` (`status` lists the names; two
devices with the same name are told apart by their keys). Removal:

- revokes every certificate of the device's key at the authority, in one
  revocation list, as a compromised key: the authority never enrolls that key
  again;
- stops the Spaces the device shares, and the Spaces only it could see;
- takes it off every other Space, whose policy then names only the devices
  still there, and turns off a folder permission from before Spaces that
  names it;
- drops it from the network computer's devices. The others drop it at their
  next refresh; a Space of theirs that stopped stops there once two listings
  in a row leave it out.

The removed device cannot renew its certificate or use the authority bridge.
Other devices refuse it once they see the revocation, within about a minute
(at most five, when a certificate ages out), and a window already being sent
may still finish. To join again, it needs a fresh setup of Connect, with a new
key. Asking again finishes a removal that failed part way. On other devices,
Forget removes only a device this device saved itself and revokes nothing.

## Choose how devices connect

**Settings → Connection** on the network computer chooses for every device:

- **Public relays** (the default): n0's public Iroh relays and address lookup
  help devices find each other from anywhere. Relays see connection metadata
  such as IP addresses and timing, never file contents, which stay end-to-end
  encrypted.
- **Private: this local network only**: no relay and no address publication.
  Devices connect directly while they share a network with the computer.

The setting changes how devices find each other, never what they may do;
Genesis Mesh still authenticates every node and authorizes every operation.
Join links carry the setting they were created under. Afterwards each device
asks the network computer for its setting with every trust refresh (every 30
seconds while running), over the authenticated authority bridge, and reopens
its connections when the setting changes. That answer also carries the
computer's current addresses; a device accepts them only for the same endpoint
it already trusts. An older network computer that cannot answer leaves the
device's setting unchanged.

A device can be stricter than its network (**Only connect on the local network
from this device**), never looser. Changing the setting keeps every pairing
and identity; nothing is paired again.

In private mode, devices find each other through saved addresses and, on
Windows, macOS, Linux and Android, local network discovery (mDNS). Discovery
runs under both settings, so a device that has not yet heard of a switch to
private still finds its network computer on the same network. iPhones rely on
saved addresses until Connect has Apple's multicast entitlement. Guided devices
reuse their listening port after a restart, so saved addresses stay valid; if
another program has taken the port, a new one is used and devices with
discovery find it.

Under public relays only, a desktop's own endpoints ask the router to open a
port (UPnP, NAT-PMP, PCP), which can improve direct connections; on macOS the
router probe may show a local network prompt. Private mode never asks the
router to open an internet-facing port. Your own relay on an always-on server,
for private connections away from home, is planned.

## Share and browse

A shared folder is a **Space**. Any Windows, macOS or Linux device of the
network can share one, not only the network computer: choose **Files → Share
a folder** and select the folder with the native picker. The Space takes the
folder's name and, for now, is shared with every other device of the network
(choosing devices comes next). A device shares up to 16 Spaces; a network
holds up to 64.

The network computer issues every Space. A device asks it over the
authenticated authority bridge; the network computer's owner runtime then
creates one boundary policy for that Space, naming exactly its devices, and
an attestation for the sharing device's own subject. A device can only share
its own folders, only with devices the network computer saved (or the network
computer itself), and only it can change or stop its Spaces. The network
computer keeps the list of Spaces (name, sharing device, devices) in its owner
directory, so recovery files include it.

**Files** lists the Spaces on your network: this device's, marked **Shared
from this device**, and each Space another device shares with this one, by
the sharing device's name, even while that device is off. Choose **Open** to
browse it; the files come straight from the sharing device, which asks the
authority for a decision on each page and each download. Every device learns
the list with its trust refresh. **Stop sharing** stops serving the Space on
the device at once and deactivates its policy, so no decision allows it
afterwards, even from a device that kept serving the folder; files other
devices already saved stay on them. If the network computer cannot be reached
at that moment, the device asks again at its next refresh, and the network
computer removes again any of its own Spaces it no longer shares. A new Space
never takes over an existing permission: a device cannot claim a folder another
device shares, or one shared before Spaces. Devices list Spaces from a copy the
network computer refreshes every 30 seconds, so a busy network computer never
holds up their file operations. There are no remote path fields in the normal
UI.

The everyday interface has Files, Devices and Settings, with bottom navigation
on phones. Choose a device by name to browse its files. Technical controls and
error details stay in Settings > Advanced.

Metadata-only catalog pages require their own authenticated proof and
`connect.collection.list` decision. Downloads use disk-backed snapshots and a
fresh `connect.collection.read` decision for each short transfer window. The
policy always receives the **full file size**, never the window size. Signed
receipts and window hashes are verified, and the whole-file SHA-256 must match
before native viewing/export. No local paths or bulk bytes cross frontend IPC.

Current bounds: up to 16 Spaces per device, up to 16 subfolder levels, files up to
1 GiB, at most 512 entries scanned per folder, pages of 32, one active transfer
per Space,
bounded cache/receipt storage. Links, junctions, unsafe
names and oversized files are omitted; source versions are checked on each
window. Downloads offer progress/cancel, small UTF-8 text previews and OS
view/save actions. Android FileProvider covers only the verified-download cache.
Tap a folder to open it; use the breadcrumbs to return to its parent or the
shared root. Search filters the current folder. Each directory component is
opened through a capability-relative no-follow handle. Directory segments are
bound to the signed browse intent and nested-download token, and the authority
receives the relative file path for any path-based read gates. A download
can continue from where it stopped: when the sharing device no longer has its
snapshot (after 15 minutes, or a restart), it takes a fresh one of the same
version and serves from the offset, and each window is still decided for the
whole file; a file that changed in between is refused, and the app's check of
the whole file's digest never lets two versions mix. While the app runs it
asks a broken window again for up to about two minutes, reaching the device
afresh each time; a sharing device that is busy (its download limits, two
snapshots already being prepared, or a network computer it could not ask in
time) is asked again the same way; only a decision that says no, or a
certificate it refuses, ends the download. A download
nobody has continued for a minute, for example a canceled one, gives its
place to a new one, and can still go on later from a fresh snapshot.
Snapshots a previous run left behind, for example after a crash, are removed
the first time the app opens that Space again. The app keeps
its token until the sharing device no longer has it or refuses it, then asks
without it; asked without a token, the sharing device first continues a
snapshot it already has of the same file for the same device, and makes a
fresh one only when it has none. A refusal without a token ends the
download. The app does not yet keep unfinished downloads across its own
restarts. Mobile folder sharing remains pending.

Existing 64-KiB permissions stay unchanged. **Share a folder again** and select
the folder to issue a new larger-file permission. Both apps need the new build
for nested browsing: the new Browse ALPN and nested Download v2 have distinct
proof/exporter domains. Legacy flat list/catalog/download remains available for
older clients, including installed build 5.
Mobile viewing, export and large-file physical acceptance are still pending.

A Space's policy and attestation last 90 days. The network computer renews
every Space with less than 30 days left once a day, and the sharing device
picks up the renewed attestation at its next refresh without interrupting
transfers. Renewal keeps a Space's devices as its host chose them, including a
device the network computer has since forgotten; that device cannot renew its
own certificate, so it loses access within a day, and revoking it is part of
Requests. A folder the network computer shared before Spaces existed becomes
a Space under its folder name, shared with every saved device, the first time
the updated app runs there. An app from before Spaces still browses the first
Space shared with it. Saved sharing is restored only for the guided consumer
flow, after its authority is rebound; older advanced profiles still reopen
unshared.

## Send files

A device can receive files into an **inbox**: on a Windows, macOS or Linux
device, choose **Files → Receive files** and pick the folder files should land
in. The inbox is a Space of its own kind: the network computer issues a
policy that lets the chosen devices (for now, every other device) write into
it, and nothing else. An inbox is never browsed, and a shared folder never
accepts files. **Stop receiving** works like stopping any Space.

Other devices see **Send files to Home PC** in Files; **Send a file** opens
the native picker and shows progress, then the name the file was saved under.
The receiving device decides every step:

- The sender declares the file's name, size and SHA-256. For each window of
  bytes the receiving device asks the authority whether that sender may write
  the **whole file** into this inbox, with a fresh decision, before it accepts
  a byte; splitting a file into windows never passes a size gate.
- Bytes go to private staging on the receiving device. Each window is signed
  by the sender over its hash, and the receiving device signs a receipt for it.
- The file is saved only when its whole SHA-256 matches what the sender
  declared, under its own name or "name (2).ext" and so on: an existing file
  is never replaced. The receiving device keeps the signed receipts, its last
  one confirming the whole file; the sender verifies each receipt and is told
  the name the file was saved under. A file that changes on the sending
  device while it is sent stops at the next window.

Current bounds: files up to 1 GiB, windows of 64 KiB to 32 MiB sized to the
connection, up to four unfinished incoming files and 2 GiB of staging per
inbox, and an hour before an abandoned file is dropped. Windows from
several senders take turns; one that waits more than ten seconds, finds
the inbox full (before its budget or an authority request is spent), goes over
its rate, or whose decision the device could not get from its network computer
in time, is told the device is busy rather than refused, and the app tries
that window again for a few minutes. Only a decision that says no, or a
certificate it refuses, refuses the file. A network computer that keeps
failing for another reason, for example an attestation it no longer knows,
also shows as busy until the app stops asking. One sender keeps at most two
unfinished files in an inbox. A window at the wrong place in its file is
refused, so a file's bytes and its checked hash always agree. The file is
written under a temporary name starting with a dot and given its name by a
hard link, which never replaces a file; on drives without hard links (FAT,
exFAT) the name is reserved first and written in place. A name too long to
take " (2)" is refused before any byte is sent. Staging is
claimed only after the authority allows the file, and each sender has its
own rate limit. Every window of a download or a send asks the authority anew.
Devices ask through the network computer's bridge, whose budgets bound the
whole network (480 decisions and attestation reads a minute, about 240
windows); the authority Connect runs accepts that much from the bridge's one
loopback address, while each device keeps core's own limit of 120 decisions
a minute. The network computer's own Spaces ask its authority directly,
within that per-device limit. The apps size windows to the connection, up to
32 MiB, so ordinary transfers stay well within it. An authority attached
from an existing configuration keeps core's default limits, which allow
about 120 windows a minute for the whole network.

An interrupted send continues where it stopped. The receiving device keeps an
unfinished file's bytes and a small record (sender, file, digest, how much has
arrived) in its private staging for an hour (on Linux and macOS, readable
only by the app's user); a window that breaks off is cut back to what was
recorded rather than lost.
While the sending app runs, it asks a broken window again for up to about two
minutes, reaching the device afresh each time. A window at the wrong place,
for example after a lost confirmation, is answered with where the file
stands, and only its own sender is told. The sending app learns a transfer's
token as soon as the receiving device names it, so even a file sent in one
window can be asked again. A saved file is remembered for 10 minutes, across
restarts of either device: its last window asked again, after a lost
confirmation, is answered with the name it was saved under instead of the
file being saved again. A device that stopped while saving a file looks for
it in the inbox when it starts again within the hour its staging is kept:
found under one of the names it chooses from, written since, with the same
size and digest, it is remembered as saved; otherwise the file is still
staged and continues. Sending the same file again (same
sender, inbox, name, size and digest), for example after the sending app
restarted, continues the file already there instead of starting another; a
transfer the device no longer has is answered with "start again", which the
app does once. After the receiving device restarts, the whole-file hash is
worked out again from the staged bytes before the file is saved. Sending
from phones, and phones receiving files, need the phone builds' file pickers
and are not available yet.

## Verification boundary

The real-authority integration suite verifies pairing and final mutual session
proofs, remote enrollment, list/read capability separation, bounded pages,
file-version changes, policy denial and authority outage. It runs both device
identities on one host. Windows UI setup uses a disposable network and bundled
runtime. iOS compile/archive/install results and physical Windows/iPhone pairing,
Keychain persistence, browsing and lifecycle tests must be recorded separately
in [two-device acceptance](two-device-acceptance.md).
